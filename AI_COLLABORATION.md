# Building MacWiki with AI

MacWiki is an experiment in using AI agents as collaborators on a substantial native macOS application. This document describes the working method behind the commit history. It is not a claim that every line was generated by AI, nor that generated output was accepted without review.

## Division of Responsibility

The human role owns:

- product direction and taste
- feature scope and acceptance criteria
- decisions about what is ready to keep
- correction of inaccurate assumptions
- final evaluation of the running application

AI agents contribute:

- codebase mapping and implementation proposals
- SwiftUI and AppKit implementation work
- regression investigation
- test generation and maintenance
- documentation and evidence capture
- repetitive refactors and release checks

This division matters. The useful unit of work is not a prompt followed by generated code; it is a claim about the product followed by implementation, evidence, criticism, and revision.

## The Control System

### A durable source of truth

Product vision, architecture, engineering constraints, and acceptance criteria are stored in project documents. Chat sessions are treated as temporary working context rather than the authority on what MacWiki is supposed to do.

### Small, inspectable commits

The repository preserves hundreds of incremental commits across design passes, feature work, bug fixes, accessibility improvements, tests, and quality evidence. This makes it possible to inspect how a decision evolved and to revert a narrow change without discarding unrelated work.

### Behavioral evidence

Tests should exercise behavior. A test that merely reads a Swift file and asserts that it contains a modifier or type name does not prove that the application works. Where behavior is difficult to reach, MacWiki extracts policies and collaborators into testable boundaries.

### Honest feature boundaries

Documentation is expected to match the source tree. Readwise-related model fields exist, but authentication and synchronization do not. The project therefore describes Readwise sync as deferred instead of presenting scaffolding as a shipped feature.

### Safety around persistence and QA

The app treats silent persistence failure as data loss. Save operations route through a reporting boundary rather than disappearing inside `try?`. QA harnesses isolate their state so automated checks do not mutate the operator's real reading library.

### Performance and accessibility as product requirements

The project does not treat smooth scrolling, keyboard navigation, reduced-transparency behavior, or contrast as cleanup work. They are part of the product contract and can block a candidate from being considered ready.

## Representative Experiments

- Building a four-column SwiftUI interface around an AppKit split-view shell.
- Extracting testable policies from large views and web-view coordinators.
- Coordinating native toolbar commands with focused-window and focused-scene behavior.
- Making Liquid Glass presentation respond to user preference, Reduce Transparency, and Increase Contrast through one runtime policy.
- Replacing silent SwiftData saves with a persistence boundary that reports failures.
- Separating tests of MacWiki's logic from tests that genuinely require live Wikipedia.
- Maintaining a candidate-based internal-beta program with reproducible evidence and isolated QA state.

## What Has Not Worked

AI collaboration creates its own failure modes. Generated tests can reward code shape instead of behavior. Local fixes can enlarge already-overgrown views. Documentation can describe an intended architecture as though it already exists. A successful build can be mistaken for proof of a usable interface.

MacWiki's process rules are largely the residue of those failures. They require agents to extract boundaries before extending hotspots, distinguish current behavior from aspiration, and validate the running application when the claim is about the interface.

The aim is not to hide the role of AI or to present generated volume as accomplishment. The aim is to make the collaboration legible enough that someone else can judge the decisions, the safeguards, and the resulting software.
